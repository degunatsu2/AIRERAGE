## A. 発見した設計上の問題・矛盾（優先して判断が必要）

### P-1. 永久コンボが成立しうる【重要度: 高】

**内容**: 仕様の3つのキャンセル規則を組み合わせると、次のループが成立しうる。

```
攻撃 →(キャンセル1回)→ 攻撃 → ワイヤー射出 → 牽引中 → 攻撃 →(キャンセル)→ 攻撃 → ワイヤー → …
```

「攻撃→攻撃は1チェーン1回」のカウンタがワイヤーを挟んでリセットされる場合、ループを止めるのはワイヤーのクールダウンだけになる。リセットされない場合はコンボが短くなり、「ワイヤーと攻撃キャンセルを組み合わせた立体コンボ」というコンセプトが弱まる。

**選択肢と推奨**: D-17（キャンセルのリセット条件）と D-22（被弾中の方向転換）で判断する。推奨は「ワイヤー牽引でリセットする（コンボの自由度を確保）＋コンボ補正・強制ダウン・コンボ中のワイヤー回数上限で永久を防ぐ」。

**決定（2026-10-12、ユーザー）**: **攻撃のワイヤーキャンセルにクールタイムを設けて対策する**。
- 攻撃をワイヤーでキャンセルした瞬間にエフェクトを出す。
- クールタイム中は、キャラクターの周囲に**半透明の円形ゲージ型クールタイマー**を表示し、クールタイム中であることを見て分かるようにする。
- 解釈（Claude の仮定。異なる場合は指摘してほしい）: このクールタイムは「攻撃をワイヤーでキャンセルする行為」にだけかかる。通常移動中のワイヤー射出は、短い再射出クールダウンだけで使える（2026-10-12 に変更: 接続の解除後のクールダウンは 0、外れた後は【仮】20ティック）。クールタイムの長さは【仮】180ティック（3秒）から調整する。
- コンボ補正・強制ダウンなどの追加対策は採用せず、必要になったら再検討する。

### P-2. 「引っ張られている状態」の定義次第でタイプA/Bが不公平になる【重要度: 高】

**内容**: 「ワイヤー→攻撃キャンセルは、ワイヤーで引っ張られている状態に限り可能」とされている。この状態を物理的な張力で定義すると、タイプA（振り子。張力がかからない瞬間がある）とタイプB（常に牽引）で攻撃キャンセルできる時間が変わり、タイプ選択による不公平な性能差になる。

**推奨**: 物理量ではなく**フェーズで定義**する。両モデル共通の `Attached` フェーズを「牽引中」とし、キャンセル判定はモデルに依存させない（D-18）。

**決定（2026-10-12、ユーザー）**: 推奨どおり。ワイヤーがオブジェクトと接続している状態を**「接続中」フェーズ（`Attached`）**と定義し、その間だけワイヤー→攻撃のキャンセルを可能にする。

### P-3. ホスト権威と空中コンボの遅延が衝突する【重要度: 高・技術的に最大のリスク】→ ロールバックの採用で解消（2026-10-12）

**内容**: ホストが命中を確定する方式では、攻撃側の画面で相手が打ち上がるのは、入力がホストに届き、結果が戻ってきた後になる（往復遅延＋補間遅延）。追撃を素早くつなぐ空中コンボは、この遅延の影響を最も受けやすい。

**選択肢**: 状態同期＋クライアント予測＋ラグ補償＋ヒットストップによる遅延の隠蔽（推奨・初期案）／決定論的ロールバック（格闘ゲームでの標準）。詳細と移行判断の基準は [04_network.md](04_network.md)。

**推奨**: Phase 2 のネットワーク技術検証で遅延を模擬して評価し、判断基準を満たさなければロールバックへ移行する。どちらにも対応できるよう、シミュレーションは最初から「固定ティック・純C#・入力コマンド駆動・状態を明示的に持つ」形で作る。

**ユーザーの方針（2026-10-12）**: 方式の指定はなし。**ホストとクライアントの双方が遅延を感じにくい方式**を優先する。→ 推奨案（状態同期＋予測）で始め、Phase 2 の判断ゲートでは「ホスト側・クライアント側の両方で遅延を感じにくいか」を評価基準に加える。満たせなければロールバックへ移行する。

**決定（2026-10-12、ユーザー）**: 格闘ゲームで採用されている**決定論的ロールバック**にする（ユーザーの好み）。空中コンボで相手の反応が往復遅延分遅れる問題はなくなり、ホストとクライアントが同じ条件になる。代わりに、予測が外れたときの巻き戻しと、PC 間の完全な決定性が課題になる（対策は [04](04_network.md) の 3.3 と 3.5）。

### P-4. 戦闘報酬がコインを「生む」と、インフレと戦闘偏重を招く【重要度: 中】

**内容**: 「ダメージや撃破でもコインを獲得できる」をコインの生成として実装すると、戦闘が多い試合ほどコインが増え、マップのコインの価値が相対的に下がり、回収型の戦術が成立しにくくなる。

**推奨**: 戦闘報酬は主に「相手の所持コインをドロップさせる（移動させる）」形にし、生成は撃破ボーナスの少額だけに限定する（[01 の3章](01_game_design.md)、D-24）。

**決定（2026-10-12、ユーザー）**: 推奨は**不採用**。「移動」中心の経済では戦闘を起こす行為そのものの価値が薄くなるため、**ダメージや撃破でコインを獲得する（生成する）現状のスタイルを維持**する。戦闘以外の稼ぎは、ハプニングイベントなどで増やす方針をユーザーが検討する。
- 影響: [01 の3章](01_game_design.md) の戦闘報酬を「生成」中心に改める。インフレと戦闘偏重への対策は、同じ相手への報酬の減衰・上限と、戦闘以外の稼ぎ（ハプニングイベント、フィールドコイン）の比率の調整で行う。具体的な仕様は Phase 4 で決める。

### P-5. 4人乱戦とガード、ジャストガードとラグ補償【重要度: 中】

**内容**:
- 方向を指定するガードは、4人乱戦では背後や上空からの攻撃に対して不公平になる。
- ラグ補償（攻撃側から見えていた位置で命中を判定する）は攻撃側に有利な方式で、防御側のジャストガードの入力タイミングとずれる。

**推奨**: ガードは全方向にする。ジャストガードの判定は、防御側の入力ティックを基準に一定の許容幅で行う（防御側に寄せる）。Phase 3 で遅延を模擬して検証する。

### P-6. 入力デバイスによる照準精度の差【重要度: 中】

**内容**: マウスで自由に照準できると、ゲームパッドよりワイヤーの照準が正確になり、対戦で有利になる。

**推奨**: 全デバイスで「方向入力＋エイムアシスト」を基本にする。マウス照準は後から検討するオプションにする（D-08）。

**決定（2026-10-12、ユーザー）**: キーボード＋マウスでは、マウスポインターの方向へ射出する（キーボードだけでは8方向にしか撃てないため）。ゲームパッドは左スティックの方向＋エイムアシストのまま。
- 残る課題: オンライン対戦では、マウスの方が照準が正確になる可能性がある。Phase 2 以降の対戦の検証で差を確かめ、必要ならエイムアシストの強さをデバイスごとに調整する。

**プレイテストの結果（2026-10-13、#3）**: 黄色いアンカーポイントを狙うときだけ、エイムアシストに引っ張られるような感覚がある（タイプA／Bとも △）。エイムアシストは照準から ±12° 以内のアンカーポイントへ向きを補正するので、マウスのように狙いが正確な機器では、補正が「引っ張り」に感じられる。対応の候補: 角度を全体で小さくする、マウスのときだけ弱める（デバイスごとの調整。どの機器かを入力に含める必要がある）、そのまま。**決定（2026-10-13、ユーザー）**: 全体の角度を小さくする（±12° → ±6°【仮】）。

**追加の決定（2026-10-12、ユーザーの提案）**: ゲームパッドは右スティックで照準できる（倒していないときは左スティックの方向）。移動の向きに関係なく、どの方向にも撃てる。射程の上限は全デバイスで同じなので、照準の自由度の差は小さくなった。
- 残る差の候補（対戦の検証で確かめる）: (1) 照準を合わせる速さと細かさ（マウスは一瞬で大きく正確に動かせる。スティックはエイムアシストで補う。デバイスごとのアシストの強さで調整する）、(2) 移動の細かさ（スティックはアナログ、キーボードは 0／1。今の移動は走行速度に直接かけるので、歩きの速さを細かく選べるのはスティックだけ。影響は小さい見込み）、(3) カメラのズームなどの表示の設定（全員が同じ範囲まで使えるようにし、上限で制限する）、(4) マクロや連射の外部ツール（入力の受付規則で防げる範囲で対策する）。

### P-7. プレイヤーホスト型の構造的な限界【重要度: 中・方針確認】

**内容**:
- ホストは遅延0で操作できる（ホスト有利）。
- ホストのプログラムを改ざんされると不正は防げない。

**推奨**: 友人同士やカジュアルな対戦では許容する。ランクマッチを作る場合は専用サーバーが必要になる。ホスト権威の設計にしておけば、同じコードを専用サーバーへ移しやすい。

**ロールバックの採用による変化（2026-10-12）**: 全員が同じシミュレーションを実行するので、ホストだけが遅延0になる有利はなくなる。送るのは入力だけなので、ホストを含めて結果の改ざんもできない（不一致として検出される）。残るのは、ホストの切断と、全状態が手元にあることによる情報の不正な表示（影響は小さい。04 の 3.7）。

**検討メモ（2026-10-12、ユーザーの質問。ロールバックの採用前）**: Steam での見知らぬ人とのランダムマッチでも、プレイヤーホスト型は成り立つ（Steam のロビーとマッチメイキング、Steam のリレー経由の通信で NAT 越えができ、サーバー代はかからない）。ただし、上の2点に加えて「ホストが抜けると試合が終わる（ホストの移行は難しい）」「ホストの回線と PC の性能に全員が左右される」が問題になりうる。自前のサーバーを持っていなくても、専用サーバーは借りる形（ゲームサーバーのホスティングサービス）で用意できるので、構造上の障害ではなく、費用と運用の問題になる。方針: 当面はホスト権威の設計のまま進め、ホストのコードを画面なしでも動かせるようにしておく（後で専用サーバーに移せるように）。Phase 2 の検証で、ホスト有利の大きさを計測して判断する（D-14、D-16）。

### P-8. ワイヤーの接続先にプレイヤーを含めると予測が難しくなる【重要度: 中】

**内容**: 他プレイヤーは補間で過去の位置に表示されるため、プレイヤーへのワイヤー接続は予測と結果のずれが大きくなる。

**推奨**: 初期は地形とアンカーポイントのみ接続可能にする。プレイヤーへの接続はネットワーク方式が固まってから再検討する（D-09）。

#### D-11. ワイヤータイプの選び方

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| (1) プレイヤーが選ぶ | キャラ選択時に、キャラとは別にA/Bを選ぶ（スト6の「クラシック／モダン」操作に近い） | 好きなキャラを好きな操作で使える。操作の好みとキャラの好みを分けられる | バランスを検証する組み合わせが「キャラ数×2」になる。相手のタイプを表示するUIが必要 |
| (2) キャラ固有 | キャラごとにA/Bが決まっている | バランスをキャラ単位で完結できる。タイプがキャラの個性になる | 好きなキャラと好きな操作が一致しないことがある。タイプ間の性能差がそのままキャラ格差になる |
| (3) 試合ごとの設定 | ホストがルールとして全員のタイプを決める | 全員が同条件で最も公平。検証が簡単 | 好みが分かれると、片方を好む人が不満を持つ。マッチングが分断される |
| (4) 組み合わせ | (1)を基本にし、ホストが「自由／A限定／B限定」を選べる | 好みと公平性の両方に配慮できる | (1)と同じ検証量に加え、ルール設定のUIが必要 |

**推奨**: プロトタイプでは実行中にA/Bを切り替えられるようにして、両方を比較する。製品としては **(4) を第一候補**にする。ただし、計測（コースタイム、接近成功率、勝率）でタイプ間の差が許容範囲に収まらない場合は、(3) に切り替える。

**ユーザーのプレイテスト（2026-10-13）**: 検証用アリーナのコースでは、タイプA の方が速く（正確には測れていない）、操作感も A が良い。B は遠心力がないので、下から上の足場に乗るのが難しく、明確に遅い。「B を削除して A 一本にした方がいいかもしれない」との意見。B を削除すると、確定している基本原則（2つのタイプ）とこの D-11 が変わるので、次から選ぶ:

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| (a) B を削除 | `ResponsiveWireModel` と B の調整値・テストを消し、A だけにする | 調整と検証が A だけで済む。タイプ間の公平性の問題（P-2 など）がなくなる | 基本原則の変更。戦闘を作った後に「別の操作感」が欲しくなったら作り直し（ただし差し替えの仕組みは残る） |
| (b) B を作り直す | B に A にない強み（例: 解除したときに勢いが残る、狙った点へまっすぐ速く行ける）を持たせる | 2タイプの方針を保てる | 作り直しと調整の手間。戦闘がない今は強みを評価しにくい |
| (c) B を凍結 | コードは残し（今も A が既定）、B の調整を止める。戦闘（Phase 3）で「速く正確に近づく」価値を確かめてから (a)/(b) を決める | 今は何も失わない。判断の材料が増える | B のテストの保守が少し残る |

**決定: (c) B を凍結**（2026-10-13、ユーザー）。B のコードとテストは残し（既定は A）、調整は止める。必要になったら（戦闘ができた後など）改めて相談する。
