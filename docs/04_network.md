# 04. ネットワーク方式の候補と技術リスク

> ステータス: ドラフト v0.1（2026-10-12）。調査日時点の情報です。各ライブラリの版や料金は、導入時に公式情報で再確認してください。

---

## 1. 前提と要件

| 項目 | 内容 |
|---|---|
| 人数 | 4人 |
| 方式 | プレイヤーホスト型（プレイヤーの1人がホストを兼ねる） |
| 権威 | ホストが試合進行と重要な結果（命中、ダメージ、ガード結果、ゲージ、コイン、撃破、勝敗）を確定する |
| 応答性 | 自分の移動とワイヤーは、遅延を感じずに反応すること |
| 特に難しい点 | 空中コンボ（攻撃側と被弾側が密接にやりとりする）、ジャストガード（タイミングが厳しい）、高速なワイヤー移動 |
| ホスト切断 | 試合を終了してよい（ホストの移行は必須ではない） |

## 2. 同期方式の候補

| 案 | 概要 | 自分の操作の応答性 | 空中コンボへの適性 | 不正への強さ | 実装の難しさ | 決定性の要求 |
|---|---|---|---|---|---|---|
| **A. 状態同期＋クライアント予測（ホスト権威）** | クライアントは入力を送り、ホストが全員分を計算して状態を配信する。自キャラは手元で予測し、ホストの結果と照合して補正する。他キャラは補間して表示する | 高い | 中（被弾の反応が往復分遅れる。ヒットストップとラグ補償で緩和する） | 高い（クライアントは入力しか送れない） | 中〜高（予測と照合を自前で作る） | 低い（ずれは照合で補正される） |
| **B. 決定論的ロールバック** | 全員の入力だけを共有し、各自が同じシミュレーションを実行する。届いていない入力は予測し、外れたら巻き戻して再計算する（GGPO方式） | 高い | **高い**（格闘ゲームの標準的な方式） | 高い（結果を偽れない） | 高い（全状態の保存と復元、完全な決定性、ずれの検出） | **非常に高い**（浮動小数点の扱いにも注意が必要） |
| C. Netcode for Entities | Unity 公式。予測とラグ補償を内蔵したサーバー権威型 | 高い | 中 | 高い | 高い（ECS / DOTS で作り直す必要がある） | 中 |
| D. Photon Fusion 2（Host Mode） | サードパーティ。予測と再計算、ラグ補償付きのヒットボックス、ホスト移行を内蔵 | 高い | 中 | 高い | 中（独自の作法に従う） | 中 |
| E. 所有者権威の移動＋ホスト権威の結果 | 各クライアントが自キャラの位置を決めて送り、命中などの結果だけをホストが確定する（NGO の NetworkTransform を所有者権威で使う） | 高い | 低い（ノックバックが被弾側を経由するため遅れる） | 低い（速度改ざんなど） | 低い | 低い |

### 2.1 推奨: 案A（状態同期＋予測）で始め、案Bへ移行できる構造にしておく

**理由**:
- 仕様の「ホストが重要な結果を確定する」にそのまま合う。
- 決定性が多少崩れても、照合で補正されるため壊れにくい。Unity と浮動小数点の環境でも安全に作れる。
- 段階的に作れる（まず自キャラの移動の予測だけ → ワイヤー → 戦闘）。
- 将来ランクマッチ用に専用サーバーへ移す場合も、ホスト権威のコードを流用できる。

**案Bへの備え**: シミュレーションは最初から「固定ティック、純C#、入力コマンド駆動、状態を明示的な構造体で持つ、決定的な乱数」で作る（[03](03_architecture.md)）。これは案Aの予測にも必要な条件で、案Bに移行する場合はネットワーク層の差し替えと、状態の保存・復元の追加が主な作業になる。

**案Bへの移行判断（Phase 2〜3 の判断ゲート）**: 往復遅延 100ms を模擬した環境で、次のどれかを満たせない場合はロールバックを本格的に検討する。
- 空中コンボの基本ルート（打ち上げ → ワイヤーで追う → 追撃）が、手元の検証で7割以上成功する
- 被弾側の位置の補正（ワープ）が目立たない（手動チェックリストで評価）
- ジャストガードの成功率が、遅延なしと比べて大きく下がらない

## 3. 推奨構成（案A）の詳細

### 3.1 データごとの権威

| データ | 権威 | クライアントでの扱い |
|---|---|---|
| 自キャラの移動・ワイヤー | ホスト（入力から再計算） | 予測して即座に表示。ホストの結果と照合し、ずれたら巻き戻して再計算する |
| 他キャラの移動・ワイヤー | ホスト | スナップショットの間を補間して表示（【仮】約100ms 遅れ） |
| 攻撃の発生 | ホスト（入力から） | 自分の攻撃は予測して即座に再生する |
| 命中・ダメージ・ガード結果 | ホスト（ラグ補償付き） | 確定を待つ。ヒットストップで待ち時間を隠す |
| ゲージ | ホスト | 予測表示してよい。確定値で上書きする |
| コイン（出現・拾得・ドロップ・確定） | ホスト（CoinLedger） | 拾得だけ見た目上で予測する（取れなかったら元に戻す） |
| 撃破・復帰・タイマー・勝敗 | ホスト | 表示のみ |

### 3.2 メッセージ

| メッセージ | 向き | 信頼性 | 内容 |
|---|---|---|---|
| 入力 | クライアント → ホスト | 信頼性なし（直近の数ティック分を毎回まとめて送り、欠落に備える） | ティック番号付きの `PlayerInput` |
| スナップショット | ホスト → クライアント | 信頼性なし | 全キャラの状態、各クライアントの「処理済みの最新入力ティック」 |
| イベント | ホスト → クライアント | 信頼性あり | 撃破、コインの取引、試合の状態変化（連番付き） |

送信頻度: 入力は 60Hz、スナップショットは【仮】30Hz から始めて計測する。

### 3.3 予測と照合

1. クライアントはホストのティックを推定し、往復遅延の半分＋余裕の分だけ先行してシミュレーションを進める。
2. 自分の入力を履歴に保存し、ホストに送る。
3. スナップショットを受け取ったら、そのティックでの予測状態と比べる。
4. 差が閾値を超えたら、スナップショットの状態に戻し、それ以降の入力を再適用して現在まで再計算する。
5. 見た目は急に飛ばさず、数フレームかけて補正する。

### 3.4 ラグ補償（命中判定）

- ホストは全キャラのやられ判定の履歴を【仮】200ms 分保持する。
- 攻撃の判定は、攻撃側の画面に表示されていた時刻まで巻き戻して行う。巻き戻しは【仮】最大150ms までにする（遅延が大きい攻撃側が有利になりすぎないように）。
- ジャストガードは防御側の入力ティックを基準に、一定の許容幅で判定する（P-5）。

### 3.5 遅延を隠す工夫

- **ヒットストップ**: 命中時に数フレーム止まる演出で、確定が届くまでの時間を自然に隠す。
- ヒットの火花や音は、予測の段階で出してよいもの（攻撃の発生など）と、確定を待つもの（ダメージ、ドロップなど）を分ける。
- ワイヤーの接続先は、初期は静的な地形とアンカーだけにする（予測が外れにくい）。

### 3.6 切断

| 状況 | 扱い |
|---|---|
| クライアントの切断 | 【仮】5秒の猶予の後にキャラを退場させる。スコアは結果に残す（所持コインの扱いは【未決】） |
| ホストの切断 | 試合を終了し、全員をメニューに戻す。途中までの結果は参考として表示する |
| ホストの移行 | 初期スコープ外（下記 4.1 参照） |

### 3.7 不正と公平性

- クライアントは入力しか送れないので、位置や結果を偽ることはできない（入力を自動化するボットは防げない）。
- ホストは遅延0で操作でき、改ざんされると不正を防げない。カジュアルな対戦では許容する（P-7）。

## 4. ライブラリ・サービスの候補

### 4.1 Netcode for GameObjects（NGO）2.x ＋ Unity Transport【推奨】

- 調査時点の最新版は v2.13.0（2026年7月頃の公開）。Unity 6.3 LTS（6000.3）からは NGO 1.x のサポートが終了しているため、2.x を使う。
- **本格的なクライアント予測と照合は内蔵されていない**。代わりに「Client Anticipation」（`AnticipatedNetworkVariable` / `AnticipatedNetworkTransform`）があるが、巻き戻して再計算する方式ではない。
- そのため、本プロジェクトでは NGO を「接続管理、オブジェクトの生成、メッセージ送受信、試合の状態の同期」に使い、**キャラクターの予測と照合は独自の入力・スナップショットメッセージで実装する**。
- ホストの移行: Unity Multiplayer Services のセッションには host migration の仕組みがあるが、標準のデータ移行処理は Netcode for Entities 向けだけで、NGO では独自の実装か Distributed Authority を使う必要がある。初期スコープ外とする。
- 推奨する理由: Unity 公式で無料、Unity 6 系に対応、仕様の方針にも挙がっている。予測を自前で作るため、ライブラリへの依存が小さく、将来の差し替えもしやすい。
- 注意: マイナー版の更新が頻繁なので、版を固定し、NGO への依存を `Degunatsu.Net` アセンブリに閉じ込める。

### 4.2 その他の候補

| 候補 | 特徴 | 本プロジェクトでの評価 |
|---|---|---|
| Netcode for Entities | 予測とラグ補償を内蔵。クライアントがサーバーを兼ねる構成にも対応 | ECS で全体を作る必要があり、GameObject ベースの開発と大きく異なる。初期の採用は見送る |
| Photon Fusion 2 | Host Mode で予測と再計算、ラグ補償付きのヒットボックス、ホスト移行を内蔵 | 機能面では有力。ただし有料（同時接続数に応じた料金。2026年時点の料金は未確認）で、独自の作法に依存する。案Aの自前実装が困難だった場合の代替候補 |
| ロールバック用ライブラリ（Backdash など） | GGPO に影響を受けた C# の実装 | 調査時点ではプレビュー版で、Unity での動作は未確認。案Bに移行する場合に評価する |
| Photon Quantum | 決定論的なエンジン（ロールバック内蔵） | 有料で、独自のシミュレーション環境で作り直す必要がある。案Bを本格採用する場合の比較対象 |
| その他のオープンソース（FishNet、Mirror など） | — | 今回は詳しく調べていない。必要になれば比較する |

### 4.3 セッション管理・NAT越え

- **開発中**: LAN または直接IPで接続する。
- **公開時**: Unity Multiplayer Services（Sessions＋Relay）で参加コードによる接続と NAT越えを行う。Relay は平均同時接続50人までと、1人あたり3GiB（最大150GiB/月）の通信量まで無料、それ以降は従量課金（Unity の料金ページの記載。最新の料金は導入時に確認する）。
- Steam で配信する場合は、Steam のネットワーク機能（中継サーバー経由のP2P）も比較する（D-16）。

## 6. Phase 2 のネットワーク技術検証（概要）

**目的**: 案Aの構成で、移動とワイヤーの同期が操作感を損なわないかを、戦闘を作る前に確かめる。

**範囲**:
1. NGO で、ホスト1人＋クライアント最大3人が接続する。
2. 入力の送信、スナップショットの配信、自キャラの予測と照合、他キャラの補間を実装する。
3. ワイヤーのフェーズと接続先を同期する。
4. ネットワークシミュレーターで、往復遅延 0 / 50 / 100 / 150ms、パケットロス 0 / 2% を模擬する。

**完了条件**: [05_roadmap.md](05_roadmap.md) の Phase 2 を参照。
