# 04. ネットワーク方式の候補と技術リスク

> ステータス: ドラフト v0.2（2026-10-12）。調査日時点の情報です。各ライブラリの版や料金は、導入時に公式情報で再確認してください。
> **2026-10-12、ユーザーの指示で同期方式を決定論的ロールバック（案B）に決めた（D-14）**。案A（状態同期＋予測）の詳細は、この文書の v0.1（git の履歴）を参照。

## 1. 前提と要件

| 項目 | 内容 |
|---|---|
| 人数 | 4人 |
| 方式 | プレイヤーホスト型（プレイヤーの1人がホストとしてセッションを管理する） |
| 同期 | **決定論的ロールバック**（D-14）。全員が入力だけを送り合い、各自が同じシミュレーションを実行する |
| 結果の確定 | 重要な結果（命中、ダメージ、ガード結果、ゲージ、コイン、撃破、勝敗）は、**全員の入力が届いて確定したティックのシミュレーション結果**を正とする。どのプレイヤーも結果そのものは送らない（送るのは入力だけ）。ホストはセッションの管理（参加、開始、終了、結果の記録）と、不一致（desync）を検出したときの裁定を行う |
| 応答性 | 自分の操作は遅延を感じずに反応すること（ホストもクライアントも同じ条件） |
| 特に難しい点 | 空中コンボ、ジャストガード、高速なワイヤー移動、4人分の入力の予測 |
| ホスト切断 | 試合を終了してよい（ロールバック方式では全員が状態を持つので、続行も技術的には可能。【未決】） |

## 2. 同期方式の候補

| 案 | 概要 | 自分の操作の応答性 | 空中コンボへの適性 | 不正への強さ | 実装の難しさ | 決定性の要求 |
|---|---|---|---|---|---|---|
| A. 状態同期＋クライアント予測（ホスト権威） | クライアントは入力を送り、ホストが全員分を計算して状態を配信する。自キャラは手元で予測し、ホストの結果と照合して補正する。他キャラは補間して表示する | 高い | 中（被弾の反応が往復分遅れる） | 高い | 中〜高 | 低い |
| **B. 決定論的ロールバック【採用】** | 全員の入力だけを共有し、各自が同じシミュレーションを実行する。届いていない入力は予測し、外れたら巻き戻して再計算する（GGPO 方式。近年の格闘ゲームで標準） | 高い（全員が同じ条件） | **高い** | 高い（結果を偽れない） | 高い（状態の保存と復元、完全な決定性、不一致の検出） | **非常に高い** |
| C. Netcode for Entities | Unity 公式。予測とラグ補償を内蔵したサーバー権威型 | 高い | 中 | 高い | 高い（ECS で作り直す） | 中 |
| D. Photon Fusion 2（Host Mode） | サードパーティ。予測と再計算、ラグ補償、ホスト移行を内蔵 | 高い | 中 | 高い | 中 | 中 |
| E. 所有者権威の移動＋ホスト権威の結果 | 各クライアントが自キャラの位置を決めて送る | 高い | 低い | 低い | 低い | 低い |

### 2.1 決定: 案B（ロールバック）

**決定（2026-10-12、ユーザー）**: 格闘ゲームで採用されているロールバック方式を使う（ユーザーの好み。D-14）。

**この方式の利点（本作にとって）**:
- 空中コンボ: 相手の動きも手元で計算するので、命中した瞬間に相手が打ち上がる（案Aのような往復遅延がない）。
- 公平性: ホストも含めて全員が同じ条件（自分の入力は遅延なし、相手の入力は予測）。案Aの「ホストだけ遅延0」がなくなる（P-7 の一部が解消）。
- 不正: 送るのは入力だけなので、位置や結果を偽れない。自分のシミュレーションを改ざんしても、不一致として検出される。
- 本作の Core は最初から「固定ティック、純C#、入力駆動、状態を構造体で持つ」形で作っており、ロールバックの前提を満たしている。

**この方式の課題**:
- **予測が外れると巻き戻る**: 相手の入力が予測と違ったとき、相手キャラの位置などが数フレーム分さかのぼって修正される（見た目では、相手が少しワープする）。対策は 3.3。
- **完全な決定性が必要**: 同じ入力から、すべての PC で1ビットも違わない結果が出る必要がある。浮動小数点の計算が PC によって変わらないかを、早めに検証する（3.5、R-11）。
- **4人分の予測**: 相手が3人いるので、誰か1人の予測が外れても巻き戻る。巻き戻しの頻度は 1対1 の格闘ゲームより高くなる。
- 途中参加と再接続には、全状態の送信が必要（状態は小さいので可能）。

## 3. 採用構成（案B: ロールバック）の詳細

### 3.1 仕組み

1. 各プレイヤーは、ティックごとの自分の入力（`PlayerInput`。量子化済み）を全員に送る。
2. 自分の入力は【仮】数ティックの入力遅延を付けて使う（3.3）。
3. 相手の入力がまだ届いていないティックは、予測した入力で進める（予測: 最後に届いた入力をそのまま続ける）。
4. 入力が届いたら、予測と比べる。違っていれば、そのティックの状態に戻して（巻き戻し）、正しい入力で現在まで計算し直す。
5. 全員の入力が届いたティックを「確定ティック」とし、それより前の状態の保存は捨てる。

**状態の保存と復元**: `SimWorld` の全状態（キャラクターの `CharacterState`、今後の戦闘・コイン・試合の状態）を値として保存・復元できるようにする。状態は構造体で持っているので、配列のコピーで済む。

**実装の置き場所**: 1〜5 は Core の `RollbackSession`（`Airerage.Core.Rollback`、通信をしない純C#）。送受信と通信路は `Airerage.Net` が受け持ち、届いた入力をセッションに渡す（[10](10_online_plan.md) 2章）。

### 3.2 データごとの扱い

| データ | 扱い |
|---|---|
| 全キャラの移動・ワイヤー・攻撃・命中・ゲージ | 全員が同じシミュレーションで計算する。予測中の結果は巻き戻しで変わりうる |
| コイン（CoinLedger） | シミュレーションの一部として全員が計算する（二重加算の防止はこれまでどおりイベントIDで行う）。最終スコアは確定ティックの値を使う |
| 撃破・タイマー・勝敗 | シミュレーションの一部。試合の結果は確定ティックで決める |
| 表示（エフェクト、音、HUD） | シミュレーションの状態を読むだけ。巻き戻しで取り消されうるもの（ヒットの火花など）は、取り消しても不自然にならないように作る |

### 3.3 予測を外しにくく、外れても目立たなくする工夫

予測が絶対に外れないようにすることはできないが、「外れる回数を減らす」「巻き戻す長さを短くする」「巻き戻しを見えにくくする」の3つで抑えられる。

| 工夫 | 内容 | 効果 |
|---|---|---|
| **入力遅延（ディレイ）** | 自分の入力を【仮】2〜3ティック（約33〜50ms）遅らせて使う。その間に相手の入力が届けば、予測そのものが要らない。遅延は回線の状態に応じて自動で調整し、プレイヤーが設定で選べるようにもする（格闘ゲームで一般的） | 最も効果が大きい。往復遅延がこれ以下の相手とは、ほとんど巻き戻らない |
| 予測は「直前の入力を続ける」 | 人の入力は 1/60 秒ごとには変わらないので、ボタンやスティックは押し続ける・倒し続けると予測すると大半が当たる | 外れる回数を減らす |
| 入力を正規化する | シミュレーションに影響しない値の変化は送らない。例: 照準の方向はワイヤーを撃つティックにしか使わないので、それ以外のティックは送らない（0 にする）。スティックの細かい揺れは量子化と小さなヒステリシスで抑える | 意味のない「予測外れ」をなくす（特にマウス照準は毎ティック変わるため重要） |
| 動きに「始動」を持たせる | 攻撃の発生フレーム、フックの飛翔時間（今は最大約0.2秒）のように、入力から結果までに時間がある動作は、巻き戻っても結果が変わる前に修正できる | 巻き戻しが見えにくい |
| 巻き戻しの見た目の補正 | 相手キャラの表示位置を、巻き戻しで飛んだ分だけ数フレームかけてなめらかに寄せる（表示だけ。シミュレーションは正しい位置）。T2-8 で実装（`CorrectionSmoother`。[10](10_online_plan.md) 3.4） | ワープが見えにくい |
| 時刻の同期 | 全員のティックの進み方をそろえる（進みすぎている側を少しだけ待たせる）。片方だけが先に進むと、もう片方の巻き戻しが増える | 巻き戻しの長さを短くする |
| 巻き戻しの上限 | 【仮】最大8ティック（約133ms）。それを超えて入力が遅れたら、届くまで待つ（一瞬止まる） | 計算量と大きなワープを防ぐ |
| 近い相手とマッチングする | Steam で配信する場合は、地域や往復遅延で相手を選ぶ | 遅延そのものを減らす |

- 計算量: 巻き戻しのたびに最大8ティック分を計算し直す。計測（2026-10-13、T2-9）では、4人のワールドの1ティックが約 12µs（クラウドの .NET 8）で、8ティックの巻き戻しでも約 0.1ms。戦闘を加えた後にもう一度測る。

### 3.4 メッセージ

| メッセージ | 向き | 信頼性 | 内容 |
|---|---|---|---|
| 入力 | 各プレイヤー → 全員（P2P。またはホスト経由で中継） | 信頼性なし（まだ確認されていない直近のティックの入力をまとめて毎回送り、欠落に備える） | ティック番号付きの `PlayerInput` |
| 確認 | 各プレイヤー → 全員 | 信頼性なし | 受け取った最新のティック番号 |
| チェックサム | 各プレイヤー → ホスト | 信頼性なし | 確定ティックの状態のチェックサム（【仮】数十ティックごと）。一致しなければ不一致としてホストが記録し、試合を止める（Phase 2 では原因の調査用） |
| セッションの制御 | ホスト → 全員 | 信頼性あり | 参加、開始ティック、乱数の種、ルール、終了 |

### 3.5 決定性の確保

- シミュレーションは純C#の `Airerage.Core` だけで行う（Unity の物理、`Time`、`UnityEngine.Random` を使わない。既存の方針）。
- 乱数は、試合の開始時にホストが配る種から作る決定的な乱数だけを使う。
- 集合の列挙順に依存しない（辞書の列挙順などを使わない）。
- **浮動小数点**: 同じビルドの Windows（x64）どうしなら、四則演算と平方根の結果は一致するはず。三角関数（`MathF.Sin` / `Cos` / `Acos`）などはランタイムやOSの実装に依存する可能性があるので、Core では使う箇所を最小限にし、必要なら自前の実装か表引きに置き換える。結論は検証で出す（R-11）。
- **検証の手段**: 入力の記録と再生（T1-9b）で、記録した入力から計算した最終状態のチェックサムを、別の PC（ユーザーの Windows とクラウドの Linux など）で比べる。Phase 2 では、試合中のチェックサムの比較で不一致を検出する。

### 3.6 切断

| 状況 | 扱い |
|---|---|
| クライアントの切断 | 【仮】5秒の猶予の後に、そのキャラを退場させる（退場はセッションの制御メッセージで、全員が同じティックに反映する） |
| ホストの切断 | 初期は試合を終了する。全員が状態を持っているので、ホストを引き継いで続行することも技術的には可能（【未決】） |

### 3.7 不正と公平性

- 送るのは入力だけなので、位置や結果を偽ることはできない。自分のシミュレーションを改ざんしても、不一致として検出される。
- 全員が全状態を持つので、本来見えない情報（画面外の相手の位置など）を不正に表示されることは防げない。本作は画面外のインジケーターで相手の位置を示す設計（01 の 4.3）なので、影響は小さい。
- 入力を自動化するボットやマクロは、どの方式でも防げない。
- ホスト有利（遅延0）はなくなる。全員が同じ条件になる。

## 4. ライブラリ・サービスの候補

**方針（D-15 の見直し）**: ロールバックの層（入力の交換、予測、巻き戻し、時刻の同期）は、Core の決定性と密に関わるので、**自前で作ることを第一候補**にし、既存のライブラリ（Backdash など）と比較して決める。通信路（トランスポート）とセッション管理だけをライブラリやサービスに任せる。

| 候補 | 役割 | 評価 |
|---|---|---|
| 自前のロールバック層（`Airerage.Net`） | 入力の交換、予測、巻き戻し、時刻の同期、不一致の検出 | 第一候補。Core の疑似ネットワーク（遅延・欠落の模擬）で、Unity なしでテストできる |
| Backdash（C#、GGPO の影響を受けた実装） | ロールバックの層 | 比較の候補。調査時点ではプレビュー版で、Unity での動作は未確認 |
| Unity Transport | 通信路（UDP） | 候補。Unity 公式で無料 |
| Steam のネットワーク機能（Steam Networking Sockets と中継） | 通信路、NAT越え、ロビーとマッチング | Steam で配信する場合の第一候補（D-16） |
| Netcode for GameObjects（NGO）2.x | 状態同期向けの仕組み | キャラクターの同期には使わない。メニューやロビーなどの補助に使うかは、通信路の選択と合わせて決める |
| Photon Quantum | 決定論的なエンジン（ロールバック内蔵） | 有料で、独自の環境で作り直す必要がある。参考にとどめる |

### 4.1 セッション管理・NAT越え

- **開発中**: LAN または直接IPで接続する。
- **公開時**: Steam で配信するなら Steam のロビーと中継（無料）、そうでなければ Unity Multiplayer Services（Sessions＋Relay）。Relay は平均同時接続50人までと、1人あたり3GiB（最大150GiB/月）の通信量まで無料、それ以降は従量課金（Unity の料金ページの記載。最新の料金は導入時に確認する）。
- ロールバックでは各プレイヤーが全員に入力を送るので、中継を使う場合も通信量は小さい（入力は1ティック数バイト）。

## 6. Phase 2 のネットワーク技術検証（概要）

**目的**: ロールバック方式で、移動とワイヤーの同期が操作感を損なわないか、決定性が保たれるかを、戦闘を作る前に確かめる。

**範囲**:
1. `SimWorld` の全状態の保存と復元、状態のチェックサム。
2. Core 内の疑似ネットワーク（遅延・欠落・揺らぎの模擬）で、入力の交換、予測、巻き戻し、時刻の同期をテストする。
3. 通信路を選び（D-15、D-16）、4人が接続して移動とワイヤーを使えるようにする。
4. 往復遅延 0 / 50 / 100 / 150ms、パケットロス 0 / 2% を模擬し、入力遅延と巻き戻しの見え方を評価する。
5. 別の PC どうしで、チェックサムが一致し続けることを確かめる。

**完了条件**: [05_roadmap.md](05_roadmap.md) の Phase 2 を参照。
