# 10. オンライン技術検証の実装計画（Phase 2、ロールバック）

> ステータス: ドラフト v0.2（2026-10-13、T2-7 の接続を追加）。数値はすべて【仮】です。方式の詳細は [04](04_network.md)、完了条件は [05](05_roadmap.md) の Phase 2。

---

## 1. 目的と範囲

**目的**: 決定論的ロールバック（D-14）で、移動とワイヤーの同期が操作感を損なわないか、PC 間で決定性が保たれるかを、戦闘を作る前に確かめる。

| 範囲に含める | 範囲に含めない |
|---|---|
| 全状態の保存と復元、チェックサム | 戦闘、コイン、試合進行（Phase 3〜4） |
| 入力の管理、入力遅延、予測、巻き戻しと再計算、確定ティック | ロビー、マッチング、公開用のセッション管理（Phase 6） |
| 入力の送信の規則（冗長送信、確認応答）、時刻の同期 | ホストの移行、途中参加、観戦 |
| 疑似ネットワーク（遅延・揺らぎ・欠落・順序の入れ替え）での自動テスト | |
| 通信路の選定と、2〜4人での接続（D-15、D-16） | |
| 相手キャラの表示の補正、遅延の模擬での評価 | |

---

## 2. 構成の方針

- **ロールバックの層（入力の管理、予測、巻き戻し、確定ティック、送信の規則、時刻の同期）は Core の中に純C#で作る**（`Degunatsu.Core.Rollback`）。ネットワークのライブラリに依存しないので、Unity なしで `dotnet test` と疑似ネットワークでテストできる。
- `Degunatsu.Net`（Unity 側）は、通信路（ライブラリ）とセッションの管理だけを受け持ち、Core のロールバックの層にメッセージを渡す。ライブラリへの依存はここに閉じ込める（D-15）。
- ロールバックの層は `SimWorld` を外から操作する（状態の保存と復元、ティックを進める）。シミュレーションのコードはロールバックを意識しない。

### 3.1 疑似ネットワークでの結果（T2-3、600 ティック、4人、乱数の種 7）

| 遅延 | 揺らぎ | 欠落 | 入力遅延 | 予測の上限 | 巻き戻し（プレイヤー0） | 最長の巻き戻し | 待ったフレーム（全員） | 全員の一致 |
|---|---|---|---|---|---|---|---|---|
| 0 | 0 | 0% | 2 | 8 | 0回 | — | 0 | ✅ |
| 2 | 0 | 0% | 2 | 8 | 0回 | — | 0 | ✅ |
| 6 | 0 | 0% | 2 | 8 | 66回 | 4 ティック | 0 | ✅ |
| 4 | 0〜3 | 10% | 2 | 8 | 66回 | 6 ティック | 0 | ✅ |
| 5 | 0〜2 | 5% | 0 | 8 | 65回 | 8 ティック | 8 | ✅ |
| 12 | 0〜4 | 20% | 2 | 8 | 64回 | 8 ティック | 1404 | ✅ |
| 3 | 0 | 0% | 2 | 0（ロックステップ） | 0回 | — | 1196 | ✅ |

（遅延と揺らぎはフレーム数。1フレーム = 1/60 秒）。T2-4〜T2-6 の後も同じ結果（送受信を `InputExchange` とバイト列に置き換え、入力の正規化と時刻の同期を加えた）。

**通信量（T2-4。T2-6 でメッセージの頭が 11 → 16 バイトになったので、それぞれ約 5 バイト増える）**: 1つのメッセージの平均は、片道2フレームで 35 バイト、片道6フレーム（往復 200ms）で 82 バイト、片道4〜7フレーム・欠落10%で 74 バイト。確認応答が返るまでの入力を毎回送るので、往復の時間に比例して増える。相手1人につき毎秒60回送るので、往復 200ms で相手1人あたり約 5KB/秒、3人で約 15KB/秒の送信になる（必要なら、同じ入力が続く部分をまとめて減らせる。R-8）。遅延が入力遅延以下なら巻き戻しは起きない。遅延が予測の上限を超えると、入力が届くまで待つ（画面が止まる）。どの条件でも、最後は全員が同じ状態になり、確定した状態も途中でずれなかった。入力遅延と予測の上限を両方 0 にすると互いに待ち続けて進めないので、設定の検査で拒否する。

### 3.2 時刻の同期の効果（T2-6、1200 ティック、4人、プレイヤー0の時計だけが速い）

| 速さの違い | 通信 | 予測の上限で止まった回数（同期なし → あり） | 進み具合の差の平均（ティック） |
|---|---|---|---|
| 10%速い | 片道3フレーム | 113 → 0 | 6.8 → 3.5 |
| 10%速い | 片道6フレーム、揺らぎ0〜2、欠落5% | 114 → 67 | 1.8 → 1.6 |
| 1%速い | 片道6フレーム、揺らぎ0〜2、欠落5% | 12 → 1 | 1.0 → 0.4 |
| 同じ速さ | 片道2フレーム | 0 → 0（待たない） | 0 |

止まる（画面が一瞬固まる）代わりに、少しずつ待って速さをそろえる。実際の PC の時計の違いは 1% よりずっと小さいが、処理落ちで一時的に遅れた側に、もう一方が合わせるのにも使う。どの条件でも、最後は全員が同じ状態になった。

### 3.3 Unity での接続の構成（T2-7）

| 部分 | 内容 |
|---|---|
| 通信路 `TransportLink` | Unity Transport の薄い包み。ライブラリへの依存はここだけ。経路は2つ: 信頼性なし（入力。失われても次のメッセージで送り直す）と、信頼性・順序・分割あり（参加、開始、チェックサム） |
| メッセージ `NetMessages` | 先頭1バイトが種類: Welcome（番号の通知）、Start（人数と調整値の JSON）、Input（宛先の番号＋`InputMessage`）、Checksum、Refused（満員か試合中） |
| セッション `OnlineSession` | 1人分の試合（MonoBehaviour ではないので、テストで複数を同じプロセスで動かせる）。ホスト（プレイヤー 0）に全員がつながる星形で、クライアントどうしの入力はホストが宛先へ中継する（中継しても `InputMessage` は送り手から宛先へのものなので、確認応答と時刻の同期は1対1のまま）。試合中の参加はできない |
| 調整値 | ホストが試合の開始時に、調整値（`CharacterConfig`）を JSON で全員に送る。ホストも同じ JSON から作った値を使うので、全員の値が一致し、試合中にアセットを編集しても影響しない |
| 不一致の検出 | 確定した状態のチェックサムを 60 ティックごとにホストへ送り、ホストが自分の値と比べる。違えばエラーのログと画面に出す（裁定は後で決める） |
| 画面 `OnlineRunner`（`Sandbox_Online` シーン） | 左上のボタンで Host / Join / Start / Leave。自分のキャラをカメラが追い、照準の表示は自分だけ。巻き戻しの回数、予測の上限で止まったフレーム、時刻の同期で待ったフレーム、比べたチェックサムと不一致の数を表示する。位置のリセットはない（入力以外で状態を変えないため） |

**T2-7 で見つかった誤り（修正済み）**: 遅れて試合を始めた側に、相手の先のティックまでの入力がまとめて届くと、確定ティックが自分の今のティックより先になり、`RollbackSession` がまだ計算していないティックの入力を捨てていた（次のティックで例外）。捨てるのは「確定していて、計算も済んだティック」に限るよう直し、Core のテストを加えた。疑似ネットワークでは全員が同時に始めるので起きなかった。

**すでにできていること**: PC 間の決定性の最初の確認（2026-10-13）。クラウド（Linux）で記録した入力が Windows で、Windows で記録した入力（3600 ティック）がクラウドで、それぞれ同じ最後の状態になった（T1-9b の記録と再生）。

## 5. 確認方法

- T2-1〜T2-6 は Core のテスト（`dotnet test` と Unity の EditMode）で確かめる。疑似ネットワークは乱数の種を固定し、同じ結果が毎回出るようにする。
- T2-7 以降は、Unity で複数のプレイヤーを動かす手動の確認が必要（クラウドでは画面と操作感を確認できない）。通信そのものと全員の一致は、同じプロセスの中で本当の通信（127.0.0.1）を使う EditMode のテスト（`Degunatsu.Net.Tests`）で確かめる。

### 5.1 Multiplayer Play Mode での確認の手順（T2-7）

1. エディタで `Assets/_Project/Scenes/Sandbox_Online.unity` を開く（なければメニューの「Degunatsu > Sandbox_Online シーンを作り直す」）。
2. **Window > Play Mode > Scenarios** を開き、「+」でシナリオを作る。**Editor** にチェックを入れ、**Additional Editor Instances** の「+」で 1〜3 個加える（合計 2〜4 人）。
3. 再生（Play）すると、追加のエディタが別のウィンドウで起動する。Windows のファイアウォールの確認が出たら、Unity の通信を許可する。
4. 元のエディタのゲーム画面で **Host** を押す（ポートは既定の 7777）。追加のエディタでは、Address を `127.0.0.1` のまま **Join** を押す。ホストの画面の「Players」が人数分になったら **Start**。
5. それぞれのウィンドウで動かす（ウィンドウの切り替えは Ctrl+F9〜F12 か、クリック）。キーボード＋マウスは、操作しているウィンドウにだけ入る。
6. 確認すること: 全員の画面に全員のキャラが出る／自分のキャラは入力どおりにすぐ動く（入力遅延 2 ティック）／相手のキャラが動く（巻き戻しで小さく飛ぶことがある。表示の補正は T2-8）／ホストの画面の「Desyncs」が 0 のまま／抜けた人がいると、ホストに「disconnected」と出て、全員の試合が終わる（ほかの人には「Disconnected from the host」）。
7. 別の PC との確認（LAN）: ホストの PC の IP アドレス（`ipconfig` の IPv4）を、参加する側の Address に入れる。ビルドした実行ファイルどうしでもよい（ビルドの最初のシーンを Sandbox_Online にする）。
