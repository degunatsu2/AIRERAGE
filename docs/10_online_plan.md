# 10. オンライン技術検証の実装計画（Phase 2、ロールバック）

> ステータス: v1.0（2026-10-13、Phase 2 の完了）。数値はすべて【仮】です。方式の詳細は [04](04_network.md)、完了条件は [05](05_roadmap.md) の Phase 2。

---

## 1. 目的と範囲

**目的**: 決定論的ロールバック（D-14）で、移動とワイヤーの同期が操作感を損なわないか、PC 間で決定性が保たれるかを、戦闘を作る前に確かめる。

| 範囲に含める | 範囲に含めない |
|---|---|
| 全状態の保存と復元、チェックサム | 戦闘、コイン、試合進行（Phase 3〜4） |
| 入力の管理、入力遅延、予測、巻き戻しと再計算、確定ティック | ロビー、マッチング、公開用のセッション管理（Phase 6） |
| 入力の送信の規則（冗長送信、確認応答）、時刻の同期 | ホストの移行、途中参加、観戦 |
| 疑似ネットワーク（遅延・揺らぎ・欠落・順序の入れ替え）での自動テスト | |
| 通信路の選定と、2〜4人での接続（D-15、D-16） | |
| 相手キャラの表示の補正、遅延の模擬での評価 | |

---

## 2. 構成の方針

- **ロールバックの層（入力の管理、予測、巻き戻し、確定ティック、送信の規則、時刻の同期）は Core の中に純C#で作る**（`Airerage.Core.Rollback`）。ネットワークのライブラリに依存しないので、Unity なしで `dotnet test` と疑似ネットワークでテストできる。
- `Airerage.Net`（Unity 側）は、通信路（ライブラリ）とセッションの管理だけを受け持ち、Core のロールバックの層にメッセージを渡す。ライブラリへの依存はここに閉じ込める（D-15）。
- ロールバックの層は `SimWorld` を外から操作する（状態の保存と復元、ティックを進める）。シミュレーションのコードはロールバックを意識しない。

**通信量（T2-4。T2-6 でメッセージの頭が 11 → 16 バイトになったので、それぞれ約 5 バイト増える）**: 1つのメッセージの平均は、片道2フレームで 35 バイト、片道6フレーム（往復 200ms）で 82 バイト、片道4〜7フレーム・欠落10%で 74 バイト。確認応答が返るまでの入力を毎回送るので、往復の時間に比例して増える。相手1人につき毎秒60回送るので、往復 200ms で相手1人あたり約 5KB/秒、3人で約 15KB/秒の送信になる（必要なら、同じ入力が続く部分をまとめて減らせる。R-8）。遅延が入力遅延以下なら巻き戻しは起きない。遅延が予測の上限を超えると、入力が届くまで待つ（画面が止まる）。どの条件でも、最後は全員が同じ状態になり、確定した状態も途中でずれなかった。入力遅延と予測の上限を両方 0 にすると互いに待ち続けて進めないので、設定の検査で拒否する。

### 3.2 時刻の同期の効果（T2-6、1200 ティック、4人、プレイヤー0の時計だけが速い）

| 速さの違い | 通信 | 予測の上限で止まった回数（同期なし → あり） | 進み具合の差の平均（ティック） |
|---|---|---|---|
| 10%速い | 片道3フレーム | 113 → 0 | 6.8 → 3.5 |
| 10%速い | 片道6フレーム、揺らぎ0〜2、欠落5% | 114 → 67 | 1.8 → 1.6 |

止まる（画面が一瞬固まる）代わりに、少しずつ待って速さをそろえる。実際の PC の時計の違いは 1% よりずっと小さいが、処理落ちで一時的に遅れた側に、もう一方が合わせるのにも使う。どの条件でも、最後は全員が同じ状態になった。

### 3.3 Unity での接続の構成（T2-7）

| 部分 | 内容 |
|---|---|
| 通信路 `TransportLink` | Unity Transport の薄い包み。ライブラリへの依存はここだけ。経路は2つ: 信頼性なし（入力。失われても次のメッセージで送り直す）と、信頼性・順序・分割あり（参加、開始、チェックサム） |
| メッセージ `NetMessages` | 先頭1バイトが種類: Welcome（番号の通知）、Start（人数、試合の番号、調整値と試合のルールの JSON）、Input（試合の番号＋宛先の番号＋`InputMessage`）、Checksum（試合の番号つき）、Refused（満員か試合中）、Hello（クライアント → ホスト: プレイヤーネーム。ロビーで変えるたびに送る。ホストが Start の JSON に全員の名前を入れる。docs/12 3.8）、Lobby（ホスト → クライアント: 番号ごとに、つながっているかとプレイヤーネーム。だれかがつながる・抜ける・名前を変えるたびに送る。待機所の表示に使う）。試合の番号は再戦（docs/12 3.4）のため。今の試合のものだけを使う |
| セッション `OnlineSession` | 1人分の試合（MonoBehaviour ではないので、テストで複数を同じプロセスで動かせる）。ホスト（プレイヤー 0）に全員がつながる星形で、クライアントどうしの入力はホストが宛先へ中継する（中継しても `InputMessage` は送り手から宛先へのものなので、確認応答と時刻の同期は1対1のまま）。試合中の参加はできない |
| 開始の送り直し（2026-10-14） | 配布したビルドでの通信対戦で、結果の「Restart」を押すとゲームが始まらずに止まった（ユーザーの報告）。ホストだけが新しい試合を始め、クライアントに開始のメッセージが届かない（送れない）と、両方とも相手の入力を待って止まる。対策: ホストは開始のメッセージを、そのクライアントから新しい試合の入力が届く（始めた）まで 0.5 秒ごとに送り直す。クライアントは同じ試合の開始のメッセージが重ねて届いたら無視する。開始のメッセージは約 4KB で、Unity Transport の分割の既定の上限（4KB）に近かったので、上限を 16KB にした。送れなかったときと、調整値が不正な開始のメッセージはログに出す。ビルドでの再現はできていないので、原因の候補をまとめて塞いだ（✅ Unity のバッチモードで確認済み: 再戦の直後の 1.5 秒、クライアントへのメッセージを全部落としても、送り直しで同じ試合になり、同じ状態になる） |
| 待機所（2026-10-14） | ロビーでは、ホストもクライアントも画面の中央に待機所を出す（`WaitingRoomPanel`）。番号ごとの札で、つながっている人はプレイヤーの色の縁と名前（「HOST」「YOU」の印）、まだいない番号は「WAITING...」。ホストは下の「START」で始める。ロビーで抜けた人の番号は空き、始めるときに詰める（番号が変わる人には Welcome を送り直してから Start を送る。以前は、途中の番号が空いたまま始めると、番号が人数を超える人が出ていた） |
| 調整値 | ホストが試合の開始時に、調整値（`CharacterConfig`）を JSON で全員に送る。ホストも同じ JSON から作った値を使うので、全員の値が一致し、試合中にアセットを編集しても影響しない |
| 不一致の検出 | 確定した状態のチェックサムを 60 ティックごとにホストへ送り、ホストが自分の値と比べる。違えばエラーのログと画面に出す（裁定は後で決める） |
| 画面 `OnlineRunner`（`Sandbox_Online` シーン） | 左上のボタンで Host / Join / Leave（Start は待機所）。自分のキャラをカメラが追い、照準の表示は自分だけ。巻き戻しの回数、予測の上限で止まったフレーム、時刻の同期で待ったフレーム、比べたチェックサムと不一致の数を表示する（試合中は「Details」で開く。T3-8）。位置のリセットはない（入力以外で状態を変えないため）。T3-8 から、ステージはアスレチックステージ（ステージの範囲・ギミック・4人分の出現位置。`OnlineStage`）で、右上に撃破の数を出し、コンボの表示と効果音もある（docs/11 3.13） |

**T2-7 で見つかった誤り（修正済み）**: 遅れて試合を始めた側に、相手の先のティックまでの入力がまとめて届くと、確定ティックが自分の今のティックより先になり、`RollbackSession` がまだ計算していないティックの入力を捨てていた（次のティックで例外）。捨てるのは「確定していて、計算も済んだティック」に限るよう直し、Core のテストを加えた。疑似ネットワークでは全員が同時に始めるので起きなかった。

### 3.4 表示の補正と遅延の模擬（T2-8）

| 部分 | 内容 |
|---|---|
| 位置の修正量 | `OnlineSession` は、届いた入力で巻き戻して計算し直すたびに、各キャラクターの今の位置が変わった量を記録する（`ConsumeCorrection`）。補間に使う直前のティックの位置も同じだけずらすので、表示はちょうどその量だけ飛ぶ。回数と最大量を画面に出す（Corrections / Largest） |
| 表示の補正 `CorrectionSmoother` | 飛んだ量の逆向きのずれを表示に足し、ずれを時間とともに指数的に小さくする（時定数【仮】0.08 秒。約 0.25 秒でほぼ消える）。【仮】3m を超える修正は寄せずにすぐ正しい位置に出す。シミュレーションの状態は変えない。画面の「Smooth corrections」で切り替えて比べられる |
| 遅延の模擬 | Unity Transport のシミュレーター（追加のパッケージは不要）で、自分が送るパケットに遅延・揺らぎ・欠落を加える。画面で Off / RTT 50 / RTT 100 / RTT 150（片道 0 / 25±3 / 50±5 / 75±8ms）と、欠落 0 / 2 / 5% を選ぶ。往復の遅延を模擬するには、全員で同じ値を選ぶ |

補正するのはキャラクターの位置だけ。ワイヤーのフックや接続点は補正しない（巻き戻しで相手のフックが急に進んで見えることがある。目立つなら後で考える）。

- 巻き戻しの回数は、遅延が入力遅延を超えると、どの条件でも 1 分に 380〜550 回（人の入力は相手3人の合計で 1 秒に約 9 回変わる）。巻き戻しの平均の長さは、入力遅延 2F で往復 100ms なら 1.3F、150ms なら 2.2F、200ms なら 3.9F。目立つかどうかは回数ではなく、飛ぶ距離で決まる。
- ユーザーの確認（T2-8）と合う: 往復 100ms ではワープが 1 分に 6 回・最大 0.44m で、気にならない。150ms・欠落 5% では 1 分に 22 回・最大 0.92m で、少し見える。
- 入力遅延を 1F 増やすと、ワープはおよそ 3 分の 1 になるが、すべての操作が 17ms 遅れる。
- 計算量: 4人のワールドを1ティック進めるのは約 12µs（クラウドの .NET 8。Unity の Mono ではもっと遅い）。8ティックの巻き戻しでも約 0.1ms で、1フレーム（16.7ms）に対して十分小さい。
- 疑似ネットワークでは全員が同じ速さで進むので、時刻の同期で待つことはなかった。実際の PC では、処理落ちなどで待つことがある（待つとその間、自分のキャラが止まって見える）。

**すでにできていること**: PC 間の決定性の最初の確認（2026-10-13）。クラウド（Linux）で記録した入力が Windows で、Windows で記録した入力（3600 ティック）がクラウドで、それぞれ同じ最後の状態になった（T1-9b の記録と再生）。

## 5. 確認方法

- T2-1〜T2-6 は Core のテスト（`dotnet test` と Unity の EditMode）で確かめる。疑似ネットワークは乱数の種を固定し、同じ結果が毎回出るようにする。
- T2-7 以降は、Unity で複数のプレイヤーを動かす手動の確認が必要（クラウドでは画面と操作感を確認できない）。通信そのものと全員の一致は、同じプロセスの中で本当の通信（127.0.0.1）を使う EditMode のテスト（`Airerage.Net.Tests`）で確かめる。

### 5.1 Multiplayer Play Mode での確認の手順（T2-7）

1. エディタで `Assets/_Project/Scenes/Sandbox_Online.unity` を開く（なければメニューの「Airerage > Sandbox_Online シーンを作り直す」）。
2. **Window > Play Mode > Scenarios** を開き、「+」でシナリオを作る。**Editor** にチェックを入れ、**Additional Editor Instances** の「+」で 1〜3 個加える（合計 2〜4 人）。
3. 再生（Play）すると、追加のエディタが別のウィンドウで起動する。Windows のファイアウォールの確認が出たら、Unity の通信を許可する。
4. 元のエディタのゲーム画面で **Host** を押す（ポートは既定の 7777）。追加のエディタでは、Address を `127.0.0.1` のまま **Join** を押す。ホストの画面の「Players」が人数分になったら **Start**。
5. それぞれのウィンドウで動かす（ウィンドウの切り替えは Ctrl+F9〜F12 か、クリック）。キーボード＋マウスは、操作しているウィンドウにだけ入る。
6. 確認すること: 全員の画面に全員のキャラが出る／自分のキャラは入力どおりにすぐ動く（入力遅延 2 ティック）／相手のキャラが動く（巻き戻しで小さく飛ぶことがある。表示の補正は T2-8）／ホストの画面の「Desyncs」が 0 のまま／抜けた人がいると、ホストに「disconnected」と出て、全員の試合が終わる（ほかの人には「Disconnected from the host」）。
7. 別の PC との確認（LAN）: ホストの PC の IP アドレス（`ipconfig` の IPv4）を、参加する側の Address に入れる。ビルドした実行ファイルどうしでもよい（ビルドの最初のシーンを Sandbox_Online にする）。

### 5.2 表示の補正の確認の手順（T2-8）

1. 5.1 と同じように 2 人以上で試合を始める（2 人で十分）。
2. **全員の画面で**、同じ遅延（例: 「RTT 100」）を選ぶ。欠落は最初は「Loss 0%」。
3. 片方のウィンドウで、左右の切り返し、ジャンプ、ワイヤーの射出と解除を繰り返す。もう片方のウィンドウで、そのキャラの動きを見る。画面の「Corrections」が増えていけば、巻き戻しで位置が修正されている。
4. 「Smooth corrections」のチェックを外したときと付けたときで、相手キャラのワープ（瞬間移動）の見え方を比べる。
5. 「RTT 150」や「Loss 2%」「Loss 5%」でも同じように見る。止まる（Stalled が増える）か、ホストの「Desyncs」が増えないかも見る。
6. 確認すること: 補正ありの方がワープが目立たないか／補正のせいで相手の動きが遅れて・ぬるっと見えないか（時定数を変えたいときは Online オブジェクトの「Smoothing」の値を変える）／自分のキャラの反応は遅延を選んでも変わらないか。

### 5.3 別の PC での決定性の確認（T2-9）

1. Windows で最新の版を取り込み、Unity の **Window > General > Test Runner** を開く。**EditMode** で `RecordedReplayTests` を選び、**Run Selected** を押す。クラウド（Linux）で作った記録（`InputRecordings/cloud_linux_typeA.txt` / `typeB.txt`）を再生し、最後の状態が一致すれば成功（ロープの巻き付きを加えた後の版で、Linux と Windows が同じ結果になる）。
2. Sandbox_Wire で F5 を押して記録を始め、ロープの巻き付き（細い壁の上の角をまたいで振る）、ジャンプ、ワイヤーの射出と解除を 30 秒ほど行い、もう一度 F5 で保存する。保存したファイル（`InputRecordings/rec_日時.txt`）をチャットに添付する（クラウドの Linux で同じ最後の状態になるかを確かめる）。
3. （PC が2台あれば）LAN で 5.1 の 7 の手順でつなぎ、数分動かして、ホストの「Desyncs」が 0 のままかを見る。

### 5.4 待機所と再戦の確認の手順（2026-10-14）

1. ビルドを配って（または Multiplayer Play Mode で）、1 人がホスト、ほかの人が Join する。
2. 待機所: ホストとクライアントの両方の画面の中央に「WAITING ROOM」と 4 つの札が出る。つながった人の札はプレイヤーの色で名前が出て、自分の札に「YOU」、1 番に「HOST」。まだいない番号は「WAITING...」が明滅する。だれかが名前を変える・抜けると、全員の札がすぐ変わるか。
3. 途中の番号の人が抜けてから「START」→ 残った人で始まり、全員が動けるか（番号が詰まる）。
4. 再戦: 試合を最後まで（短くするなら「Match」→「Duration Ticks」を 3600）遊び、結果の「Restart」を何回か押す → 毎回、全員の画面で新しい試合が始まるか。止まったら、ホストとクライアントの `Player.log`（Windows は `%USERPROFILE%\AppData\LocalLow\DefaultCompany\AIRERAGE\Player.log`）の「OnlineSession:」の行を送ってほしい。
