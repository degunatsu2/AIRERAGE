# 10. オンライン技術検証の実装計画（Phase 2、ロールバック）

> ステータス: ドラフト v0.1（2026-10-13）。数値はすべて【仮】です。方式の詳細は [04](04_network.md)、完了条件は [05](05_roadmap.md) の Phase 2。

---

## 1. 目的と範囲

**目的**: 決定論的ロールバック（D-14）で、移動とワイヤーの同期が操作感を損なわないか、PC 間で決定性が保たれるかを、戦闘を作る前に確かめる。

| 範囲に含める | 範囲に含めない |
|---|---|
| 全状態の保存と復元、チェックサム | 戦闘、コイン、試合進行（Phase 3〜4） |
| 入力の管理、入力遅延、予測、巻き戻しと再計算、確定ティック | ロビー、マッチング、公開用のセッション管理（Phase 6） |
| 入力の送信の規則（冗長送信、確認応答）、時刻の同期 | ホストの移行、途中参加、観戦 |
| 疑似ネットワーク（遅延・揺らぎ・欠落・順序の入れ替え）での自動テスト | |
| 通信路の選定と、2〜4人での接続（D-15、D-16） | |
| 相手キャラの表示の補正、遅延の模擬での評価 | |

---

## 2. 構成の方針

- **ロールバックの層（入力の管理、予測、巻き戻し、確定ティック、送信の規則、時刻の同期）は Core の中に純C#で作る**（`Degunatsu.Core.Rollback`）。ネットワークのライブラリに依存しないので、Unity なしで `dotnet test` と疑似ネットワークでテストできる。
- `Degunatsu.Net`（Unity 側）は、通信路（ライブラリ）とセッションの管理だけを受け持ち、Core のロールバックの層にメッセージを渡す。ライブラリへの依存はここに閉じ込める（D-15）。
- ロールバックの層は `SimWorld` を外から操作する（状態の保存と復元、ティックを進める）。シミュレーションのコードはロールバックを意識しない。

## 3. タスク分解と進捗

| タスク | 内容 | 状態 |
|---|---|---|
| T2-1 全状態の保存と復元 | `SimWorld` の全状態（ティック数と全キャラクターの状態）のスナップショット（`WorldSnapshot`、使い回せる）、復元、ワールドのチェックサム | 完了（2026-10-13）。✅ 自動テスト済み（dotnet 4件） |
| T2-2 ロールバックのセッション | `RollbackSession`: プレイヤーごとの入力の管理、入力遅延、予測（直前の入力を続ける。何も届いていなければ空の入力）、届いた入力が予測と違えば巻き戻して再計算、確定ティック、予測の上限（超えたら進めずに待つ）、確定した状態のチェックサム、巻き戻しの統計 | 完了（2026-10-13）。✅ 自動テスト済み（dotnet） |
| T2-3 疑似ネットワークでの検証 | Core のテストで、4人分のセッションを遅延・揺らぎ・欠落ありの疑似ネットワーク（冗長送信と確認応答つき）でつなぎ、全員の状態が本当の入力だけで計算した結果と一致すること、確定した状態が途中でずれないこと、入力遅延が遅延以上なら巻き戻しが起きないことを確かめる | 完了（2026-10-13）。✅ 自動テスト済み（dotnet 7条件。結果は 3.1） |
| T2-4 入力の送信の規則 | `InputMessage`（相手1人へのメッセージ: 送り手、確認応答、連続した入力。バイト列は 11 バイト＋入力1つにつき 6 バイト）と `InputExchange`（確認されていない自分の入力を覚えて毎回まとめて送り直す、届いたメッセージをセッションに渡す、確認された入力を捨てる、1メッセージ最大255入力）。T2-3 の疑似ネットワークもこれとバイト列を通して動かす | 完了（2026-10-13）。✅ 自動テスト済み（dotnet 8件＋T2-3 の7条件） |
| T2-5 入力の正規化 | 照準の方向はワイヤーを撃つティックにしか使わないので、それ以外では送らない（予測の外れを減らす。04 の 3.3）。入力の記録の形式との互換も扱う | 未着手 |
| T2-6 時刻の同期 | 各プレイヤーのティックの進み方の差を測り、進みすぎている側を少し待たせる | 未着手 |
| T2-7 通信路と Unity での接続 | 通信路を選び（D-15、D-16。パッケージの追加は承認を得る）、`Degunatsu.Net` で2〜4人を接続する。Multiplayer Play Mode かビルドで動かす | 未着手 |
| T2-8 表示の補正 | 巻き戻しで相手キャラの位置が飛んだとき、表示だけを数フレームかけて寄せる | 未着手 |
| T2-9 評価と値の決定 | 往復遅延 0 / 50 / 100 / 150ms、欠落 0 / 2% を模擬して、入力遅延と予測の上限の値を決め、02 に記録する。別の PC どうしでチェックサムが一致し続けることを確かめる | 未着手 |

### 3.1 疑似ネットワークでの結果（T2-3、600 ティック、4人、乱数の種 7）

| 遅延 | 揺らぎ | 欠落 | 入力遅延 | 予測の上限 | 巻き戻し（プレイヤー0） | 最長の巻き戻し | 待ったフレーム（全員） | 全員の一致 |
|---|---|---|---|---|---|---|---|---|
| 0 | 0 | 0% | 2 | 8 | 0回 | — | 0 | ✅ |
| 2 | 0 | 0% | 2 | 8 | 0回 | — | 0 | ✅ |
| 6 | 0 | 0% | 2 | 8 | 66回 | 4 ティック | 0 | ✅ |
| 4 | 0〜3 | 10% | 2 | 8 | 66回 | 6 ティック | 0 | ✅ |
| 5 | 0〜2 | 5% | 0 | 8 | 65回 | 8 ティック | 8 | ✅ |
| 12 | 0〜4 | 20% | 2 | 8 | 64回 | 8 ティック | 1404 | ✅ |
| 3 | 0 | 0% | 2 | 0（ロックステップ） | 0回 | — | 1196 | ✅ |

（遅延と揺らぎはフレーム数。1フレーム = 1/60 秒）。T2-4 の後も同じ結果（送受信を `InputExchange` とバイト列に置き換えた）。

**通信量（T2-4）**: 1つのメッセージの平均は、片道2フレームで 35 バイト、片道6フレーム（往復 200ms）で 82 バイト、片道4〜7フレーム・欠落10%で 74 バイト。確認応答が返るまでの入力を毎回送るので、往復の時間に比例して増える。相手1人につき毎秒60回送るので、往復 200ms で相手1人あたり約 5KB/秒、3人で約 15KB/秒の送信になる（必要なら、同じ入力が続く部分をまとめて減らせる。R-8）。遅延が入力遅延以下なら巻き戻しは起きない。遅延が予測の上限を超えると、入力が届くまで待つ（画面が止まる）。どの条件でも、最後は全員が同じ状態になり、確定した状態も途中でずれなかった。入力遅延と予測の上限を両方 0 にすると互いに待ち続けて進めないので、設定の検査で拒否する。

**すでにできていること**: PC 間の決定性の最初の確認（2026-10-13）。クラウド（Linux）で記録した入力が Windows で、Windows で記録した入力（3600 ティック）がクラウドで、それぞれ同じ最後の状態になった（T1-9b の記録と再生）。

## 4. 初期パラメータ（すべて【仮】）

| 項目 | 値 | 備考 |
|---|---|---|
| 入力遅延 | 2 ティック（約33ms） | 自分の入力を何ティック後のティックに使うか。T2-9 で決める |
| 予測の上限 | 8 ティック（約133ms） | 確定していないティックをこれ以上進めない（届くまで待つ） |

---

## 5. 確認方法

- T2-1〜T2-6 は Core のテスト（`dotnet test` と Unity の EditMode）で確かめる。疑似ネットワークは乱数の種を固定し、同じ結果が毎回出るようにする。
- T2-7 以降は、Unity で複数のプレイヤーを動かす手動の確認が必要（クラウドでは画面と操作感を確認できない）。
