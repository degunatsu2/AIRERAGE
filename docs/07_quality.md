# 07. テストと品質管理の方針

> ステータス: ドラフト v0.1（2026-10-12）

---

## 1. 品質基準と確認方法

「コンパイルが通る」は品質の最低条件にすぎません。次の基準を、それぞれ決まった方法で確認します。

| 品質基準 | 主な確認方法 |
|---|---|
| 入力に対する反応が一貫している | 決定性のテスト（同じ入力列 → 同じ状態）、先行入力のテスト、手動チェックリスト |
| ワイヤーの挙動が予測可能で、調整できる | 物理の検算テスト（振り子の周期など）、契約テスト、データ駆動であることの確認、手動チェックリスト |
| 攻撃・キャンセル・ガードの条件が仕様どおり | 状態遷移の表に基づくテスト（すべての遷移の可否を網羅する） |
| ゲージとコインが正しく加算・消費される | 台帳の不変条件（総量の保存、冪等性）のテスト、シナリオテスト |
| キャラクターやルールを追加しても既存機能が壊れにくい | 全キャラクターのデータに対して同じテストを実行する、CI で常にテストする |
| オンラインで重要な結果が正しく同期される | 疑似ネットワーク（遅延・欠落の模擬）でのテスト、複数クライアントでの手動確認 |
| エラーの原因を追跡しやすい | 握りつぶさないエラー処理、遷移失敗の理由の表示、入力の記録と再生 |
| 実際に遊んで面白いかを継続的に確認できる | フェーズごとの手動プレイテスト、主観評価の記録、計測値の比較 |

---

## 2. テストの層

| 層 | 対象 | 実行環境 | 実行のタイミング |
|---|---|---|---|
| **単体テスト** | Core のロジック（移動、ワイヤー、状態遷移、台帳など） | `dotnet test`（クラウド環境・CI）と Unity Test Runner（EditMode）の両方。同じソース | 変更のたび |
| **シナリオテスト** | 入力列を流して、結果の状態を検証する（例: 「ワイヤーで足場Aから足場Bへ移動できる」） | 同上 | 変更のたび |
| **契約テスト** | 差し替え可能な部品（ワイヤーモデル、キャラクターのデータ）が共通の規則を守るか | 同上 | 変更のたび |
| **ネットワークのロジックテスト** | 入力の交換、予測と巻き戻し、時刻の同期、チェックサムによる不一致の検出。Core 内の疑似ネットワークで遅延・欠落・順序の入れ替えを模擬する | 同上 | Phase 2〜 |
| **PlayMode テスト** | シーンの読み込み、Unity 側のアダプターの接続（最小限） | Unity Test Runner | 主要な変更時 |
| **手動プレイテスト** | 操作感、視認性、面白さ | Unity Editor / ビルド | フェーズの区切り、調整時 |
| **計測** | コースタイム、最高速、勝率、報酬の内訳など | ゲーム内のログ | 調整時 |

方針:
- ロジックはできるだけ Core に置き、Unity 無しでテストできるようにする。
- PlayMode テストは壊れやすく遅いので、最小限にする。
- 不具合を直すときは、先にその不具合を再現するテストを書く。

---

## 3. 継続的インテグレーション（CI）

- **GitHub Actions** で、push のたびに `dotnet test tools/CoreTests` を実行する（Unity のライセンスが不要なので、すぐに導入できる）。
- Unity の Test Runner を CI で動かす（GameCI など）のは、Unity のライセンスを CI に設定する必要があるため、Phase 3 以降に検討する。

---

## 4. 静的チェックとコード規約

- `tools/CoreTests` のビルドでは、警告をエラーとして扱う。
- `LangVersion` を Unity と同じ C# 9 に固定し、Unity でコンパイルできない構文を検出する。
- `.editorconfig` で書式を統一する。
- Core の asmdef で `noEngineReferences: true` を設定し、UnityEngine への依存を防ぐ。
- 毎ティックの処理ではメモリを確保しない（GC による引っかかりを防ぐ）。構造体と事前に確保したバッファを使う。

## 5. パフォーマンスの目安（【仮】）

| 項目 | 目安 |
|---|---|
| フレームレート | 対象のPCで 60fps 以上を維持する |
| シミュレーション1ティック（4人分） | 0.5ms 未満（予測の再計算で、1フレームに10ティック分を計算しても余裕があるように） |
| 毎ティックのメモリ確保 | 0 バイト（Core） |

## 6. タスク完了の定義（Definition of Done）

1. 完了条件をすべて満たしている。
2. 自動テストを追加・更新し、すべて通っている。
3. 調整用の数値がコードに直接書かれていない。
4. Unity 上で確認が必要な項目は、確認したか、「未検証」と手順を明記している。
5. 報告に、変更内容、実行した検証、実行できなかった検証とその理由、残課題、次のステップを含めている。

### 検証の報告の書き方

| 表記 | 意味 |
|---|---|
| ✅ 自動テスト済み（dotnet） | このクラウド環境で `dotnet test` を実行して通った |
| ✅ Unity のバッチモードで確認済み | このクラウド環境の Unity（バッチモード）で、コンパイルやテストが通った（[08](08_cloud_unity_setup.md)） |
| ✅ Unity で確認済み | ユーザーが Unity Editor で確認し、結果を報告した |
| ⚠️ 未検証 | 実行できる環境がないため未確認。確認の手順を添える |

確認していないものを、確認済みのように報告しません。
